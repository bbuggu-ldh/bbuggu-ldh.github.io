프로파일링을 반복하는 도구

2026 · 케이스 노트

대전 에셋사업에서는 기존 ICVFX 구성 대신 Pixera를 사용하는 송출 환경으로 작업했다. 기존 환경에서는 프레임이 잘 나왔지만 이번 구성에서는 프레임이 크게 떨어져 더 많은 최적화가 필요했다.

작업 시간이 부족해 반복 측정에 드는 시간을 줄이고자 stat 값, Insights trace, 씬 구조를 함께 추출하는 Editor Utility를 만들었다. 데이터를 모으는 단계와 결과를 해석하는 단계를 나눠 반복해서 씬을 살펴볼 수 있도록 구성했다.

수집과 해석을 나누기#

현재 보고 있는 뷰에서 Insights trace와 stat rhi, stat gpu, stat scenerendering, 씬 구조 스냅샷을 추출한다. 수집한 자료는 분석 템플릿과 함께 리뷰 도구에 전달한다.

text
Editor Utility
  ├─ Insights trace
  ├─ stat rhi / gpu / scenerendering
  └─ 씬 구조 스냅샷
          ↓
분석 템플릿 + 리뷰 도구
          ↓
씬 조건과 대조하여 조치 결정

데이터 추출까지 자동화하고, 리뷰는 팀원이 쓰던 도구에서 생성하도록 했다. 모든 단계를 하나의 도구로 고정하지 않은 운영 방식이다.

숫자와 함께 수집한 맥락#

데이터확인할 수 있는 내용
actors / mesh_stats배치, 삼각형, LOD, Nanite, 머티리얼
material_stats마스터, 블렌드 모드, WPO 사용 여부
textures해상도, 포맷, 메모리
vsm_shadow_diagnosticsnon-Nanite 그림자 캐스터와 mobility 분류
frame_timing / gpu_passes프레임 타이밍과 GPU 패스

기본 stat에 없는 그림자 캐스터 분류도 함께 수집했다. 개수가 많다는 사실만으로는 어떤 오브젝트를 먼저 살펴봐야 하는지 알 수 없기 때문이다.

경고를 그대로 따르지 않은 이유#

기존 케이스에는 그림자 캐스터 개수가 많다는 경고를 씬 조건과 대조한 사례가 있다. 다수는 Nanite였고 정적 오브젝트여서, 전체 개수보다 움직이는 non-Nanite 캐스터를 구분하는 일이 중요했다.

도구의 경고는 확인할 곳을 가리키는 단서다. 실제 비용은 Nanite 여부, mobility, 라이트와 플랫폼 조건을 함께 보고 판단해야 한다.

팀에서 사용한 방식#

제출한 경력기술서에 따르면 한 씬 판독에 하루~이틀이 걸리던 수작업을 버튼 한 번의 데이터 추출과 사람의 리뷰로 나눴다. 운영 기록상 하루 8회의 측정·수정·재측정 사이클을 확보했다. 파트 4명 중 2명은 도구를 직접 사용했고, 나머지 2명은 정리된 리포트를 받아 작업했다.

버튼 한 번으로 분석 전체가 끝난다는 의미는 아니다. LLM 분석 템플릿으로 만든 보고서도 사람이 씬 조건과 대조해 판독했다.

그림자 캐스터 7,567개에 대한 경고가 있었지만 96%가 Nanite였고 대부분 정적이었다. 기록에서는 실제 갱신 비용을 확인할 대상을 움직이는 non-Nanite 187개로 좁혔다. 캐스터 수만으로 전체 그림자 비용을 판단하지 않은 사례다.

현재 범위와 후속 작업#

현재 기록은 단일 PC를 기준으로 한다. 여러 렌더 노드의 캡처를 통합하는 작업과, 씬 조건에 따라 경고 임계값을 조절하는 작업이 후속 과제로 남아 있다.

분석 템플릿도 프로젝트에 맞춰 수동으로 조정한다. 이 소개는 수집과 해석의 구조를 설명하며, 도구가 모든 병목을 자동으로 판정한다는 뜻은 아니다.
