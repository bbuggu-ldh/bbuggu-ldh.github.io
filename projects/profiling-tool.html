프로파일링을 반복하는 도구

측정할 때마다 손으로 모으던 stat과 씬 정보를 한 번에 추출하고 사람이 조건을 대조해 읽는 도구를 만들었다.

제작 과정 읽기 ↓

대전 에셋사업 / 제작 도구
2026

아래로 스크롤 ↓

대전 에셋사업에서는 기존 ICVFX 구성과 달리 Pixera를 사용하는 송출 환경으로 작업했는데 기존 환경보다 프레임이 크게 떨어져 추가 최적화가 필요했다.

작업 시간이 부족해 반복 측정에 드는 시간을 줄이려고 stat 값과 Insights trace, 씬 구조를 함께 추출하는 Editor Utility를 만들었다. 데이터를 모으는 단계와 결과를 해석하는 단계를 나눠 씬을 반복해서 살펴볼 수 있게 구성했다.

수집과 해석을 나누기#

현재 보고 있는 뷰에서 Insights trace와 stat rhi, stat gpu, stat scenerendering, 씬 구조 스냅샷을 추출해 분석 템플릿과 함께 리뷰 도구에 전달한다.

text
Editor Utility
  ├─ Insights trace
  ├─ stat rhi / gpu / scenerendering
  └─ 씬 구조 스냅샷
          ↓
분석 템플릿 + 리뷰 도구
          ↓
씬 조건과 대조하여 조치 결정

데이터 추출까지는 자동화하고 리뷰는 팀원이 쓰던 도구에서 이어가도록 해 모든 단계를 하나의 도구에 고정하지 않았다.

숫자와 함께 수집한 맥락#

데이터확인할 수 있는 내용
actors / mesh_stats배치, 삼각형, LOD, Nanite, 머티리얼
material_stats마스터, 블렌드 모드, WPO 사용 여부
textures해상도, 포맷, 메모리
vsm_shadow_diagnosticsnon-Nanite 그림자 캐스터와 mobility 분류
frame_timing / gpu_passes프레임 타이밍과 GPU 패스

기본 stat에 없는 그림자 캐스터 분류도 함께 수집했다. 개수만으로는 어떤 오브젝트를 먼저 살펴봐야 할지 알기 어려웠기 때문이다.

경고를 그대로 따르지 않은 이유#

기존 케이스에서는 그림자 캐스터 개수가 많다는 경고를 씬 조건과 대조했다. 다수가 Nanite 정적 오브젝트였기 때문에 전체 개수보다 움직이는 non-Nanite 캐스터를 구분하는 일이 중요했다.

도구의 경고는 확인할 곳을 가리키는 단서라 실제 비용은 Nanite 여부와 mobility, 라이트, 플랫폼 조건을 함께 보고 판단해야 한다.

팀에서 사용한 방식#

제출한 경력기술서에서는 한 씬 판독에 하루~이틀이 걸리던 수작업을 버튼 한 번의 데이터 추출과 사람의 리뷰로 나눴다고 기록했다. 운영 중에는 하루 8회의 측정·수정·재측정 사이클을 확보했고 파트 4명 중 2명은 도구를 직접 사용했으며 나머지 2명은 정리된 리포트를 받아 작업했다.

버튼 한 번으로 분석이 끝나는 것은 아니어서 LLM 분석 템플릿으로 만든 보고서도 사람이 씬 조건과 대조해 판독했다.

그림자 캐스터 7,567개에 대한 경고 중 96%는 Nanite였고 대부분 정적이었다. 그래서 기록에서는 실제 갱신 비용을 확인할 대상을 움직이는 non-Nanite 187개로 좁혀 캐스터 수만으로 전체 그림자 비용을 판단하지 않았다.

현재 범위와 후속 작업#

현재 기록은 단일 PC 기준이며 여러 렌더 노드의 캡처를 통합하고 씬 조건에 따라 경고 임계값을 조절하는 작업이 남아 있다.

분석 템플릿도 프로젝트에 맞춰 수동으로 조정한다. 따라서 이 도구는 수집과 해석을 돕는 흐름이며 모든 병목을 자동으로 판정하지 않는다.
